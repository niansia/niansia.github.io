## 為什麼讀這篇

前幾天讀 V-Skip，它從推理鏈那一側壓縮，提醒我不要把「看到的東西」一起刪掉。這篇剛好從另一側下手：壓縮的是視覺 token。

減少視覺 token 的方法很多，FastV、VisionZip 都是代表，但它們幾乎都在一開始（prefill）就決定好留哪些，之後整段生成都用同一批。對直接回答的模型來說這很合理，可是現在的視覺語言模型會先想幾千個 token 才回答，一開始選的那一批，真的能撐完整段推理嗎？VisionPulse 正面回答了這個問題，也被 ICML 2026 接受，所以我把它讀完。

## 這篇在做什麼

**先看一個現象。** 作者在 Qwen3-VL-4B-Thinking 推理時，記錄每一步生成的 token 分給圖片的注意力總量（論文叫 visual attention mass），看到三件事：

1. **依賴是一陣一陣的。** 寫到「來看看選項」這種純文字的步驟，幾乎不看圖；寫到「方形通風口」、「門把」這種具體物體時，看圖的量就衝上去。
2. **看的位置一直在換。** 注意力集中的區域，會跟著當下寫到的東西移動。
3. **一開始最不知道該看哪。** prefill 時模型要生的第一個字只是「So」，注意力分散，對之後要看哪裡幾乎沒有線索。靜態剪枝偏偏就是在這個時間點做決定。

另外還有一個他們叫「耦合瓶頸」的現象：整段推理一直開著全部的視覺 token，模型反而會被不相干的東西帶走。論文的例子是問「紅綠燈是綠的嗎」，模型看到車都停著，就推論燈一定是紅的，而不是直接看燈本身。

**再看做法。** VisionPulse 不需要訓練：

- 每生成一個 token，就在第 17 層（跟對照的 FastV 同一層）算這個 token 對每個視覺 token 的注意力，所有 head 平均當成重要度，之後的層只留前 K 名。
- K 不是固定的。作者發現「看圖的總量」和「真正被看到的 token 數」高度相關（不同門檻下的 Pearson r 在 0.82 到 0.95 之間），所以直接用看圖的總量乘上視覺 token 數當成這一步的預算。算總量時用了溫度 τ 小於 1 的 softmax 壓掉長尾，並取 head 裡的最大值，比較保守。
- 為了跟其他方法公平比較，預算會被夾在一個範圍內：「≤10%」是 5%～10%，「≤5%」是 1%～5%。

主要模型是 Qwen3-VL-4B-Thinking，在 CharXiv、InfoVQA、ChartQA、MMStar、RealWorldQA、MMVet、MIA-Bench 七個基準上測，另外用 Qwen3-VL-8B-Thinking 和 InternVL3.5-4B-Thinking 驗證能不能推廣。

## 結果

七個基準的平均（Qwen3-VL-4B-Thinking，長度是平均生成的 token 數）：

| 方法 | 視覺 token | 平均準確率 | 平均長度 |
|:---|:---|:---|:---|
| 原模型 | 全部 | 72.68 | 1,687 |
| VisionZip | ≤10% | 43.82 | 2,603 |
| FastV | ≤10% | 38.09 | 2,753 |
| LOOK-M | ≤10% | 54.84 | 2,675 |
| VisionPulse | ≤10% | 72.69 | 1,480 |
| VisionZip | ≤5% | 39.31 | 1,996 |
| FastV | ≤5% | 35.69 | 2,187 |
| LOOK-M | ≤5% | 44.62 | 3,509 |
| VisionPulse | ≤5% | 71.35 | 1,499 |

其他幾個數字：

- **實際留得比 5% 還少**：消融實驗（RealWorldQA、MMVet、MIA-Bench）裡，動態預算平均只留 1.9% 的視覺 token，平均準確率 75.54（原模型 75.74），長度少 16.6%。固定留 1% 是 71.03，長度反而多 27.9%；固定留 5% 是 75.16；隨機分配預算（平均 3.0%）是 72.93。
- **換模型也成立**：Qwen3-VL-8B-Thinking 平均 85.72 → 85.87，InternVL3.5-4B-Thinking 72.04 → 72.63；同樣條件下 FastV 是 73.41 和 63.41。
- **速度**：批次 8、生成 1,000 個 token 時，端到端延遲在 8K、16K、32K 長的上下文分別快 1.20、1.24、1.30 倍。
- **很多 token 從頭到尾沒人看**：附錄統計，整段推理中注意力從沒超過門檻的視覺 token 佔了不小的比例。

## 讀完最在意的三件事

**第一，壓錯了，推理會變長。** 我原本以為剪掉視覺 token 只會讓模型變笨，沒想到還會變囉嗦。靜態方法在 ≤5% 時，LOOK-M 的生成長度多了 108%，準確率還是掉了 38.6%（相對值）。附錄那個通風口的例子很傳神：VisionZip 和 FastV 都斷定「圖裡沒有通風口」，FastV 那一段還反覆寫「Wait, let me check again」繞了好幾圈，看不到證據，就只能用更長的推理去補，最後又慢又錯。

這跟 V-Skip 裡 POPE 的結果是同一件事的兩種樣子：V-Skip 是推理鏈裡的視覺證據被刪掉後，模型更愛說「有」；這裡是視覺 token 被刪掉後，模型開始繞圈。所以評估壓縮方法時只看準確率不夠，生成長度和回答的偏向也要一起看。

**第二，它和 V-Skip 用的是同一個訊號。** VisionPulse 的圖 1（寫到「square」、「handle」時看圖量衝高），幾乎就是 V-Skip 說的「視覺錨點」。V-Skip 用這個訊號決定推理鏈裡哪些字不能刪，VisionPulse 用它決定這一步要給多少視覺 token。兩篇放在一起看，結論很清楚：推理鏈和視覺 token 不是兩筆分開的成本。VisionPulse 的式 1 其實直接寫出來了，解碼的總成本大約和 g·(p+v) + g² 成正比，g 是推理長度，v 是視覺 token 數，關鍵就在 g 乘 v 那一項。

**第三，它省的是計算，不是記憶體。** 這點論文沒有明講，是我從方法推出來的：每一步要選的 token 都不一樣，所以全部視覺 token 的 KV cache 都得留著；prefill 照常做，第 17 層以前照常看全部，第 17 層還要對全部視覺 token 算一次分數才能挑。真正省下來的只有之後那些層的注意力計算，這也解釋了為什麼加速只有 1.2 到 1.3 倍。所以表上的「留 5%」，和靜態方法的「留 5%」意思不一樣，後者是真的刪掉、真的省下記憶體。論文沒有報告顯存，附錄倒是試了「FastV 在 prefill 先刪一半，再加 VisionPulse」（平均 69.4 → 70.4），我覺得這才是比較實際的用法。

## 長影片加長推理：還沒有人處理的雙重爆炸

讀到最後我發現，這批工作的實驗幾乎都是圖片。VisionPulse 的式子裡寫的是「圖片或影片」，相關研究也提到影片可以有上萬個視覺 token，但七個基準全是單張圖。

這讓我一直在想影片推理模型，也就是 Video-R1 那一代會先長篇思考再回答的模型。放進 g·v 那一項來看，長影片讓 v 變成好幾萬，長推理讓 g 變成好幾千，兩個一起放大，成本是相乘的。現在的研究大多只處理一邊：壓視覺 token 的方法多半在圖片上測、推理很短；壓推理鏈的方法多半是純文字。兩邊同時爆炸的情況，我還沒看到有人正面處理。

把 VisionPulse 搬到影片上，我想到幾個問題：

- **預算公式會不會失準？** 預算是「看圖總量 × 視覺 token 數」。視覺 token 從幾百變成幾萬時，softmax 會被攤得更平，在圖片上調好的溫度 τ 不一定適用。
- **該看的地方，不只在空間上換，也在時間上換。** 推理一路講下去，常常是從一個時刻講到另一個時刻。這讓「每一步重新選」更有道理，但也更危險：前面一直沒被看過的那幾幀，可能正是最後一個問題要問的。
- **記憶體才是第一個瓶頸。** 對長影片來說，最先遇到的問題往往不是算得慢，而是根本放不下。保留全部 KV cache 的做法，在這裡幫不上最急的那個忙。

## 我的疑問

- **只跑一次？** 解碼溫度是 0.7，論文沒說有沒有重複跑。MMVet 只有 218 題、用 GPT-4o-mini 評分，相對 +1.4% 這種小幅進步，可能在雜訊範圍內。
- **對照組被放在不擅長的區間。** FastV、VisionZip 原本設計的保留比例高很多，壓到 5% 會崩潰並不意外；而且它們真的省下了記憶體，VisionPulse 沒有。如果能在相同顯存下比較，會更公平。
- **「耦合瓶頸」主要靠例子。** 紅綠燈和通風口的例子很有說服力，但都是挑出來的。我想看統計：變短的推理裡，有多少原本是在描述和問題無關的東西？
- **沒有程式碼。** 我讀的時候沒有找到公開的程式碼。

## 讀完之後想試的事

1. **量顯存**：比較完整模型、VisionPulse，以及 FastV + VisionPulse 的峰值顯存，看在顯存小的卡上實際差多少。
2. **在影片上畫看圖量的曲線**：輸入換成影片，看每一步的看圖量是不是在提到某個時刻時衝高，以及視覺 token 有幾萬個時，它和「真正被看到的 token 數」還相不相關。
3. **把生成長度當成壓縮的健康檢查**：以後看任何壓縮方法，都一起記錄準確率、生成長度和回答「有」的比例。
4. **看看那些從頭到尾沒人看的 token**：統計它們佔多少、有沒有位置或內容上的規律。

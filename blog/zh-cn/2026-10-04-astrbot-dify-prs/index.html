替 AstrBot 和 Dify 回报 bug、送 PR

这两天在 AstrBot 回报并修了 WebChat 附件互相覆盖的问题，在 Dify 回报两个 bug，其中一个自己送了 PR。记下流程、踩到的坑，还有几件没想到的小事。

2026-10-043 分钟阅读开源贡献AstrBotDify

为什么做这件事

除了自己的项目，我也想多参与别人的大型项目：读别人的 codebase、照别人的规矩写、让不认识的人审我的代码。这两天挑了两个自己会用到的项目：聊天机器人框架 AstrBot，和 LLM 应用平台 Dify。

AstrBot：同名的截屏会互相盖掉

在 WebChat 里粘贴截屏，浏览器给的文件名几乎都是 image.png。AstrBot 存附件时直接用原文件名，所以第二张会盖掉第一张，前面那则消息的图片就跟着变了。更麻烦的是，删掉一个对话时，另一个对话还在用的同名文件也会一起被删。

我先在自己电脑上跑起一个真的 AstrBot，把问题重现出来，再发了 issue #10352。接着送了 PR #10356：存盘时在文件名前面加上时间戳，画面上仍然显示原本的文件名，也补了测试。

送出后，审查机器人 Sourcery 很快留了两则意见。第一则说扩展名特别长的时候，加上前缀的文件名会超过 255 bytes，我写测试确认后发现它是对的，于是补了一个 commit 修掉，第二则是时间戳撞名的可能，我回复说明几率极低、而且项目其他地方也是同样的命名方式，所以不改。

还有个小插曲：一个当天才注册的帐号，一分钟内在我的 PR 按了三次 Approve。后来才知道这种帐号会到处乱按，GitHub 也不会把它算进去，真正有效的只有维护者的审查。

Dify：英文、表单，还有速度

Dify 的规矩明显更严：issue 一律用英文，要照固定表单填，前面还有六个自我检查要勾。

让我最意外的是竞争。Dify 一天有十几个新 issue，同一种 bug 常被好几个人分别回报，像「分页遇到相同时间戳会漏数据」就有四篇。所以每次发之前，我都会用好几组关键字，把 open 和 closed 的 issue、PR 都搜一遍。

第一个是 #43465：HTTP 请求节点把 Array[Object] 变量塞进 request body 时，用的是 Python 的格式（单引号、True、None），不是 JSON。结果 JSON body 被「修复」成不同的数据，null 变成字符串 "None"，第二笔数据甚至被吞进第一笔的字段里。发出去才几个小时，就有另一位贡献者留言接手，在 Dify 拆出去的工作流引擎 graphon 开了修正的 PR。被确认是真的 bug 很开心，但也有点可惜，因为我原本也想自己修。

这件事让我学到：想自己修，就要在 issue 里先讲，而且当天就把 PR 送出去。

所以第二个 #43469，我在最后加了一句「I'll open a PR with a fix.」。问题是 Webhook 触发器收到 JSON 数组时会直接回 500，而 SendGrid 这类服务送事件时刚好就是数组。同一天我送了 PR #43470：没有设置 body 参数时照常触发工作流，原始内容可以从 raw 变量拿到；有设置 body 参数时回 400 并说明原因，不再是 500。新加的三个测试在修正前会失败、修正后通过，webhook 相关的 148 个测试也都过了，送出前把项目要求的 lint 和类型检查也跑过一遍。

几件没想到的事

  • Dify issue 上的 review: medium 标签，不是在评 issue 写得好不好，是 ghfind 对发文者 GitHub 帐号的分数，同一个人发的每篇都一样，所以不用太在意。
  • 新贡献者的 PR，CI 要等维护者按核准才会跑。看到一整排 action_required 不是出错，只是在排队。
  • 在 Windows 上跑 Dify 的测试有不少坑：python-magic 一 import 就卡住、默认设置会对整个项目算覆盖率而慢到不行、dotenv-linter 会抱怨 CRLF，其实只是 Windows 下载代码时自动转换了换行。
  • 写 issue 时，「不用开服务器就能跑的最小重现程序 + 实际输出 + 代码链接」比长篇描述有用得多。接手修 #43465 的那位贡献者，留言里的理解和我写的根因一模一样。

接下来

两个 PR 都还在等审查，合并的话，我就算是 AstrBot 和 Dify 的正式贡献者了。手上还有一些整理好的问题，之后会照影响大小一天发一个。比起自己写项目，这种「先读懂别人的系统，再小心地改一点点」的工作很不一样，也比我想的有趣。

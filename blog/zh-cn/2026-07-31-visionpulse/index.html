VisionPulse：推理的每一步，要看的画面都不一样

VisionPulse 发现模型推理时对图像的依赖会一步一步变化，于是每一步只留下当下需要的视觉 token，只留 5% 准确率几乎不掉，推理还变短。我很喜欢这个观察；但它省的是计算不是内存，实验也都是图片，「长视频加长推理链」这个双重爆炸，还没有人正面处理。

2026-07-315 分钟阅读视觉语言模型视觉 token 压缩思考链轻量化

ICML 2026 · 精读

VisionPulse: Dynamic Visual Sparsity for Efficient Multimodal Reasoning

Hengbo Xu, Shengjie Jin, Yanbiao Ma, Zhiwu Lu

论文 ↗

为什么读这篇

前几天读 V-Skip，它从推理链那一侧压缩，提醒我不要把「看到的东西」一起删掉。这篇刚好从另一侧下手：压缩的是视觉 token。

减少视觉 token 的方法很多，FastV、VisionZip 都是代表，但它们几乎都在一开始（prefill）就决定好留哪些，之后整段生成都用同一批。对直接回答的模型来说这很合理，可是现在的视觉语言模型会先想几千个 token 才回答，一开始选的那一批，真的能撑完整段推理吗？VisionPulse 正面回答了这个问题，也被 ICML 2026 接受，所以我把它读完。

这篇在做什么

先看一个现象。 作者在 Qwen3-VL-4B-Thinking 推理时，记录每一步生成的 token 分给图片的注意力总量（论文叫 visual attention mass），看到三件事：

  1. 依赖是一阵一阵的。 写到「来看看选项」这种纯文本的步骤，几乎不看图；写到「方形通风口」、「门把」这种具体物体时，看图的量就冲上去。
  2. 看的位置一直在换。 注意力集中的区域，会跟着当下写到的东西移动。
  3. 一开始最不知道该看哪。 prefill 时模型要生的第一个字只是「So」，注意力分散，对之后要看哪里几乎没有线索。静态剪枝偏偏就是在这个时间点做决定。

另外还有一个他们叫「耦合瓶颈」的现象：整段推理一直开着全部的视觉 token，模型反而会被不相干的东西带走。论文的例子是问「红绿灯是绿的吗」，模型看到车都停着，就推论灯一定是红的，而不是直接看灯本身。

再看做法。 VisionPulse 不需要训练：

  • 每生成一个 token，就在第 17 层（跟对照的 FastV 同一层）算这个 token 对每个视觉 token 的注意力，所有 head 平均当成重要度，之后的层只留前 K 名。
  • K 不是固定的。作者发现「看图的总量」和「真正被看到的 token 数」高度相关（不同门槛下的 Pearson r 在 0.82 到 0.95 之间），所以直接用看图的总量乘上视觉 token 数当成这一步的预算。算总量时用了温度 τ 小于 1 的 softmax 压掉长尾，并取 head 里的最大值，比较保守。
  • 为了跟其他方法公平比较，预算会被夹在一个范围内：「≤10%」是 5%～10%，「≤5%」是 1%～5%。

主要模型是 Qwen3-VL-4B-Thinking，在 CharXiv、InfoVQA、ChartQA、MMStar、RealWorldQA、MMVet、MIA-Bench 七个基准上测，另外用 Qwen3-VL-8B-Thinking 和 InternVL3.5-4B-Thinking 验证能不能推广。

结果

七个基准的平均（Qwen3-VL-4B-Thinking，长度是平均生成的 token 数）：

方法 视觉 token 平均准确率 平均长度
原模型 全部 72.68 1,687
VisionZip ≤10% 43.82 2,603
FastV ≤10% 38.09 2,753
LOOK-M ≤10% 54.84 2,675
VisionPulse ≤10% 72.69 1,480
VisionZip ≤5% 39.31 1,996
FastV ≤5% 35.69 2,187
LOOK-M ≤5% 44.62 3,509
VisionPulse ≤5% 71.35 1,499

其他几个数字：

  • 实际留得比 5% 还少：消融实验（RealWorldQA、MMVet、MIA-Bench）里，动态预算平均只留 1.9% 的视觉 token，平均准确率 75.54（原模型 75.74），长度少 16.6%。固定留 1% 是 71.03，长度反而多 27.9%；固定留 5% 是 75.16；随机分配预算（平均 3.0%）是 72.93。
  • 换模型也成立：Qwen3-VL-8B-Thinking 平均 85.72 → 85.87，InternVL3.5-4B-Thinking 72.04 → 72.63；同样条件下 FastV 是 73.41 和 63.41。
  • 速度：批量 8、生成 1,000 个 token 时，端到端延迟在 8K、16K、32K 长的上下文分别快 1.20、1.24、1.30 倍。
  • 很多 token 从头到尾没人看：附录统计，整段推理中注意力从没超过门槛的视觉 token 占了不小的比例。

读完最在意的三件事

第一，压错了，推理会变长。 我原本以为剪掉视觉 token 只会让模型变笨，没想到还会变啰嗦。静态方法在 ≤5% 时，LOOK-M 的生成长度多了 108%，准确率还是掉了 38.6%（相对值）。附录那个通风口的例子很传神：VisionZip 和 FastV 都断定「图里没有通风口」，FastV 那一段还反复写「Wait, let me check again」绕了好几圈，看不到证据，就只能用更长的推理去补，最后又慢又错。

这跟 V-Skip 里 POPE 的结果是同一件事的两种样子：V-Skip 是推理链里的视觉证据被删掉后，模型更爱说「有」；这里是视觉 token 被删掉后，模型开始绕圈。所以评估压缩方法时只看准确率不够，生成长度和回答的偏向也要一起看。

第二，它和 V-Skip 用的是同一个信号。 VisionPulse 的图 1（写到「square」、「handle」时看图量冲高），几乎就是 V-Skip 说的「视觉锚点」。V-Skip 用这个信号决定推理链里哪些字不能删，VisionPulse 用它决定这一步要给多少视觉 token。两篇放在一起看，结论很清楚：推理链和视觉 token 不是两笔分开的成本。VisionPulse 的式 1 其实直接写出来了，解码的总成本大约和 g·(p+v) + g² 成正比，g 是推理长度，v 是视觉 token 数，关键就在 g 乘 v 那一项。

第三，它省的是计算，不是内存。 这点论文没有明讲，是我从方法推出来的：每一步要选的 token 都不一样，所以全部视觉 token 的 KV cache 都得留着；prefill 照常做，第 17 层以前照常看全部，第 17 层还要对全部视觉 token 算一次分数才能挑。真正省下来的只有之后那些层的注意力计算，这也解释了为什么加速只有 1.2 到 1.3 倍。所以表上的「留 5%」，和静态方法的「留 5%」意思不一样，后者是真的删掉、真的省下内存。论文没有报告显存，附录倒是试了「FastV 在 prefill 先删一半，再加 VisionPulse」（平均 69.4 → 70.4），我觉得这才是比较实际的用法。

长视频加长推理：还没有人处理的双重爆炸

读到最后我发现，这批工作的实验几乎都是图片。VisionPulse 的式子里写的是「图片或视频」，相关研究也提到视频可以有上万个视觉 token，但七个基准全是单张图。

这让我一直在想视频推理模型，也就是 Video-R1 那一代会先长篇思考再回答的模型。放进 g·v 那一项来看，长视频让 v 变成好几万，长推理让 g 变成好几千，两个一起放大，成本是相乘的。现在的研究大多只处理一边：压视觉 token 的方法多半在图片上测、推理很短；压推理链的方法多半是纯文本。两边同时爆炸的情况，我还没看到有人正面处理。

把 VisionPulse 搬到视频上，我想到几个问题：

  • 预算公式会不会失准？ 预算是「看图总量 × 视觉 token 数」。视觉 token 从几百变成几万时，softmax 会被摊得更平，在图片上调好的温度 τ 不一定适用。
  • 该看的地方，不只在空间上换，也在时间上换。 推理一路讲下去，常常是从一个时刻讲到另一个时刻。这让「每一步重新选」更有道理，但也更危险：前面一直没被看过的那几帧，可能正是最后一个问题要问的。
  • 内存才是第一个瓶颈。 对长视频来说，最先遇到的问题往往不是算得慢，而是根本放不下。保留全部 KV cache 的做法，在这里帮不上最急的那个忙。

我的疑问

  • 只跑一次？ 解码温度是 0.7，论文没说有没有重复跑。MMVet 只有 218 题、用 GPT-4o-mini 评分，相对 +1.4% 这种小幅进步，可能在杂讯范围内。
  • 对照组被放在不擅长的区间。 FastV、VisionZip 原本设计的保留比例高很多，压到 5% 会崩溃并不意外；而且它们真的省下了内存，VisionPulse 没有。如果能在相同显存下比较，会更公平。
  • 「耦合瓶颈」主要靠例子。 红绿灯和通风口的例子很有说服力，但都是挑出来的。我想看统计：变短的推理里，有多少原本是在描述和问题无关的东西？
  • 没有代码。 我读的时候没有找到公开的代码。

读完之后想试的事

  1. 量显存：比较完整模型、VisionPulse，以及 FastV + VisionPulse 的峰值显存，看在显存小的卡上实际差多少。
  2. 在视频上画看图量的曲线：输入换成视频，看每一步的看图量是不是在提到某个时刻时冲高，以及视觉 token 有几万个时，它和「真正被看到的 token 数」还相不相关。
  3. 把生成长度当成压缩的健康检查：以后看任何压缩方法，都一起记录准确率、生成长度和回答「有」的比例。
  4. 看看那些从头到尾没人看的 token：统计它们占多少、有没有位置或内容上的规律。

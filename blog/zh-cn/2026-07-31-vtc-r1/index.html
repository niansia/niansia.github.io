VTC-R1：把推理过程印成图片，当成模型的草稿纸

VTC-R1 让模型每想完一段，就把那段推理印成图片，下一轮只看「图片草稿」接着想：token 少了 3.4 倍，速度快 1.2 到 6.6 倍，准确率大多还更高。点子很漂亮，但它测的全是纯文本的数学题，草稿读得准不准也没有量；换成本来就塞满视觉 token 的视频推理，又是另一回事。

2026-07-314 分钟阅读视觉语言模型思考链长推理轻量化

arXiv 2026 · 精读

VTC-R1: Vision-Text Compression for Efficient Long-Context Reasoning

Yibo Wang, Yongcheng Jing, Shunyu Liu, Hao Guan, Rong-Cheng Tu, Chengyu Wang, Jun Huang, Dacheng Tao

论文 ↗代码 ↗

为什么读这篇

去年 DeepSeek-OCR 和 Glyph 让我印象很深：把一段文本印成图片再给模型看，用的 token 可以少好几倍，模型还读得回来。我一直在想，文档可以这样压，那推理过程呢？会长篇思考的模型，最占空间的往往就是自己写出来的那几万个 token。

VTC-R1 做的就是这件事。我同一天也读了 VisionPulse，它压的是输入的视觉 token；这篇反过来，把推理的文本变成视觉 token。两篇方向相反，放在一起读很有意思。

这篇在做什么

把长推理切成好几轮。 每一轮，模型只看「问题＋之前每一轮推理印成的图片」，接着写下一段（每轮最多 8,192 个 token）；写完就把这一段印成图片加进去，最多 8 轮。系统提示写得很直白：这些图片记录了你之前的推理，接着想，不要重来。

怎么印。 A4 大小（595×842）、72 dpi、9 号字。作者把 Glyph 默认的字体换成 DejaVuSans，因为原本的字体会把某些数学符号印错。平均一张图装大约 1,600 个文本 token，渲染 0.12 秒、图像前处理 0.02 秒，大约占总延迟的 4%。

训练数据。 用 OpenR1-Math-Inf，它是 InftyThink 从 OpenR1-Math-220K（推理由 DeepSeek-R1 产生）切出来的分段版本。清理后 60,688 题，做成 10.6 万笔训练数据、10.5 万张图；1.81 亿个文本 token 变成 5,400 万个视觉 token，压缩 3.4 倍。

模型和对照组。 在 Glyph（以 GLM-4.1V-9B-Base 为底、专门读渲染文本的模型）和 Qwen3-VL-8B 上微调。对照组是同一份数据、一次写完整段推理的一般 SFT，以及 TokenSkip（压缩比 0.8；设成 0.6 时训练会崩）。测试集是 GSM8K、MATH500、AIME25、AMC23，另外用 GPQA-Diamond 当没看过的领域。

结果

Qwen3-VL-8B（延迟以秒计）：

基准 SFT VTC-R1 SFT 延迟 VTC-R1 延迟
GSM8K 88.1 94.7 3.04 0.46（6.6 倍）
MATH500 85.4 90.0 5.36 2.49（2.2 倍）
AIME25 32.71 30.00 29.85 12.02（2.5 倍）
AMC23 75.00 77.97 11.08 6.45（1.7 倍）
GPQA-Diamond 37.4 48.5 26.88 9.57（2.8 倍）

其他几个数字：

  • Glyph 上也一样：SFT／TokenSkip／VTC-R1 在 MATH500 是 80.4／80.6／86.0，AMC23 是 60.94／59.53／64.38，GPQA-Diamond 是 38.4／35.9／46.0；延迟快 1.2 到 2.7 倍。
  • 拿掉图片会掉分：推理时不给之前的图片，AIME25 从 26.25 掉到 23.33，AMC23 从 64.38 掉到 59.53，GPQA-Diamond 从 46.0 掉到 34.3（数字和 Glyph 的结果一致）。
  • 训练也比较快：18.93 小时，一般 SFT 要 38.92 小时，因为每一笔数据的长度被限制住了。
  • 分段长度：2K、4K、6K 里，4K 整体最好。
  • 轮数越多越准：允许的轮数增加，准确率跟着上升，大约从第 5 轮开始收敛。

读完最在意的三件事

第一，点子很漂亮：不删东西，只是写小一点。 V-Skip、TokenSkip 这些方法都是「删掉不重要的 token」，难免删错；VTC-R1 一个字都不删，只是换一种更省位置的写法。就像考试时把算到一半的过程写在草稿纸上，需要时回头翻，不用全部记在脑子里。渲染只占 4% 的时间，训练时间还减半，代码也公开了，这种「换表示法」的压缩，我觉得比「挑哪些不要」优雅很多。

第二，草稿读得准不准，论文没有量。 方法那一节用几率的连锁律证明「分段生成」和「一次生成」等价，但这只在模型拿到的是原本的文本时成立；VTC-R1 拿到的是文本印成的图，模型得自己读回来，读错就不等价了。DeepSeek-OCR 报告过，压缩比小于 10 倍时 OCR 精确度大约 97%，到 20 倍时剩六成左右。VTC-R1 只压 3.4 倍，照理说在几乎无损的范围，但那是 DeepSeek-OCR 自己的模型；Glyph 和 Qwen3-VL 读 9 号字的推理能读多准，论文没有测。换字体的那段说明也显示，印的细节会影响读回的结果。「拿掉图片会掉分」证明了草稿有被用到，但没有证明它被读对。

有一个数字让我有点在意：Qwen3-VL 上唯一变差的是 AIME25（32.71 → 30.00），偏偏是最难、推理最长、轮数最多的那一个，也就是最依赖图片草稿的那一个。30 题各跑 16 次，差距换算起来不到一题，可能只是杂讯，但方向和我的直觉一致，推理越长，草稿里的数字越多，读错一个的机会就越大。

第三，进步来自图片，还是来自分段？ VTC-R1 和一般 SFT 之间其实差了两件事：推理被切成好几轮，以及前面几轮用图片记住。分段数据本身来自 InftyThink，它用文本摘要当记忆，但论文没有和它直接比，也没有「同样分段、记忆用原本的文本」的对照组。另外，两边的生成上限也不一样：一般 SFT 最多 32,768 个 token，VTC-R1 是 8 轮 × 8,192，最多 65,536 个。

延迟的算法也要注意：它是整批跑完的总时间除以生成次数，用 vLLM 批量推论，比较接近吞吐量。每一轮的上下文比较短，一次能塞进更多请求，这可能是 GSM8K 上 token 只少了 1.6 倍、延迟却快了 6.6 倍的原因之一，不一定全是视觉压缩的功劳。

放到视频推理上：视觉 token 本来就不够用

VTC-R1 测的全是纯文本题目，模型看到的图只有自己的草稿。这让我想到它和视频推理之间的距离：

  • 草稿会和视频抢同一份预算。 视频推理的输入本来就有好几万个视觉 token，再加上一页页的推理草稿，两者挤在同一个视觉信道里。像 VisionPulse 这类剪视觉 token 的方法，分不出哪些是视频里的证据、哪些是模型自己的草稿，可能会把草稿剪掉。
  • 记忆还是会一直长。 每一轮都多几张图，只是长得比文本慢 3.4 倍。DeepSeek-OCR 提过一个想法：把越旧的图缩得越小，仿真人的遗忘。但对推理来说，哪一步可以模糊、哪一步不行，并不容易判断。
  • 同一天读的两篇，刚好各管一边。 VisionPulse 压输入的视觉 token，VTC-R1 压推理链，而且一个只在图片上测、一个只在纯文本上测。视频推理模型（Video-R1 那一代）是两边同时变长的地方：视频让视觉 token 爆炸，长推理让推理链爆炸。这个交集，我目前还没看到有人处理。

我的疑问

  • 等价性的证明不适用于有损的记忆。 连锁律那段证明的是文本记忆，不是图片记忆。
  • 缺少「分段＋文本记忆」的对照组，包括和 InftyThink 直接比较。
  • 生成上限不同：32,768 对 65,536。
  • 延迟比较接近吞吐量，单一请求的延迟改善可能没有这么大。
  • 「不需要额外训练」要看怎么解读。 它不需要额外的压缩模型或多阶段训练，但还是要用 10.6 万笔数据做 SFT，而且模型要能接受数量和大小都不固定的图片。

读完之后想试的事

  1. 草稿的读回测验：拿模型自己的图片草稿，问它中间算出的某个数字或某条式子，看读错率怎么随字体大小、dpi 改变，找出开始崩的压缩比。
  2. 补两个对照组：「同样分段、记忆用原文」和「同样分段、记忆用摘要」，把分段的效果和图片的效果分开。
  3. 量单一请求的延迟：批量大小设成 1，看加速还剩多少。
  4. 放进一道有图的题目：题目本身有图时再加上推理草稿，看模型会不会把草稿和题目的图搞混，以及剪视觉 token 的方法会不会先剪掉草稿。

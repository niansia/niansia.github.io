Reroute：丢掉的视觉 token，晚点还能捡回来吗？

Reroute 把「删掉低分的视觉 token」改成「先延后，之后还能回来」，不用训练，压得越狠救回越多。它处理的是图片；我读完一直在想，同样的想法放到长视频上会碰到什么。

2026-09-144 分钟阅读视觉语言模型视觉 token 压缩定位长视频

arXiv 2026 · 精读

Reroute, Don’t Remove: Recoverable Visual Token Routing for Vision-Language Models

Cheng-Yu Yang, Shao-Yuan Lo, Yu-Lun Liu

论文 ↗代码 ↗

为什么读这篇

现在大部分减少视觉 token 的方法都是同一个套路：打分数、留下高分的、把其他的删掉，这篇却直接质疑「删掉」这个动作本身：被丢掉的东西，还有没有机会回来？

这个问题在长视频上会更尖锐。画面太多，一定要压缩才放得进模型，可是后面的问题偏偏可能问到被压掉的细节。Reroute 处理的是图片，不是视频，但它从最小的地方切进了这个问题，所以我把它读完。

这篇在做什么

先看一个现象。 一个视觉 token 重不重要，会随着解码器的深度改变。论文追踪了「穿绿色上衣的男人」这个描述里，真正落在目标框内的一个 token：它的注意力百分位在第 3 层（FastV 做决定的地方）只有 0.11，在第 8 层（PDrop 做决定的地方）是 0.25，所以两种方法都会把它删掉；可是到第 25 层，它爬到了 0.97。浅层看起来跟背景没两样的 token，到了深层却是关键证据。

做法很简单。 Reroute 沿用原本剪枝方法的打分方式（文本对图像的注意力）和同样的分段调度，只改「打完分之后做什么」：

  • 高分的 token 照常经过这一段的注意力和 FFN；
  • 低分的 token 不删，只是这一段先跳过（走残差路径，表示维持不变），到下一个决策点再和全部视觉 token 一起重新排名，分数够高就能回来。

原本的剪枝，就是「禁止回来」的特例。从公式看，两者只差在下一段的候选集合：是上一段留下来的那些，还是全部。换个角度看，这就是不用训练、拿注意力分数当路由器的 Mixture-of-Depths。因为每一段进入计算的 token 数一样，理论上的 TFLOPs 和 KV cache 都跟原本的剪枝方法同一个等级。

结果

主要看定位任务（RefCOCO 系列，预测框的 IoU 大于 0.5 算对）。下面是 LLaVA-1.5-7B（HuggingFace 版本）的平均成绩，以完整 576 个 token 的原模型当 100%：

平均留下的 token FastV FastV + Reroute PDrop PDrop + Reroute
192 45.5% 59.2% 71.3% 82.3%
128 19.8% 31.8% 53.4% 61.2%
64 0.6% 0.6% 22.2% 34.0%

几个重点：

  • 压得越狠，救得越多，但前提是要有「再看一次」的机会。 FastV 只在一层做一次决定，到 64 个 token 时几乎救不回来；PDrop 分好几段做决定，Reroute 就能从 22.2% 拉到 34.0%。
  • 换骨干也成立。 Qwen2.5-VL-7B 砍掉 88.9% 的 token 时，PDrop 从 11.1% 到 18.6%；Qwen3.5-9B 这种混合架构进步最大，砍掉三分之二时 FastV 从 31.1% 直接到 77.5%。
  • 一般问答没有变差。 在 GQA、TextVQA、MME 等八个 VQA 基准上，平均成绩和原本的剪枝差不多或更好。
  • 计算量几乎一样。 留 64 个 token 时，PDrop + Reroute 的 TFLOPs 少 77%、KV cache 少 83%，跟 PDrop 本身差不多。
  • 另外值得一提：全部实验都在一张 RTX 4090 上完成。

附录里我最在意的两件事

第一，位置编号比想像中重要。 剪枝之后，留下的 token 可以重新编成连续的位置，也可以保留原本的位置编号。在 LLaVA-1.5 上用 FastV 留 192 个 token 时，重新编号会让 RefCOCO testA 从 27.8 掉到 1.9，几乎完全失去定位能力，token 本身还在，但模型已经不知道它「原本在哪里」。

这个结果提醒我，位置信息和 token 本身一样重要。视频多了时间轴，这件事只会更重要。

第二，Qwen3-VL 上反而变差。 附录的 Qwen3-VL-8B 实验里，砍掉三分之二的 token 时，PDrop 是 69.5%，加上 Reroute 反而掉到 57.2%；只有在砍掉 88.9% 这种极端情况，才从 12.9% 进步到 19.1%。作者的解释是 Qwen3-VL 有 DeepStack（在前几层额外注入视觉特征），手动设置的调度得配合架构调整。这个结果只放在附录，正文没有提；但现在很多人用的正是 Qwen3-VL 系列，我觉得它反而是最重要的一张表。

放到长视频上：我在想的事

图片只有几百个 token，视频就不一样了。读完之后我一直在想，把「延后而不删除」搬到长视频上，会碰到哪些问题：

  1. 候选池本身就是负担。 Reroute 延后的 token 还留在串行里，只是不参与计算。图片的 576 个 token 当然留得住，长视频动辄几万个，全部的表示都留在显卡上，本身就是内存问题。
  2. 重新排名的成本会跟着变大。 Reroute 每到一个决策点，都要拿所有候选 token 算一次注意力。候选从几百个变成几万个时，光是「重新排名」这一步就不便宜了。
  3. 跳过太久的表示会不会过期？ 被延后的 token，表示停在它被跳过的那一层；如果好几段之后才回来，它带的还是浅层的特征，却要和深层的文本一起计算。论文没有分析这件事，而在视频里可能更严重：一个 token 可能同时在「深度」和「时间」上都落后。

我的疑问

  • 实际速度没有量。 论文报的是理论上的 TFLOPs 和 KV cache，作者也承认实际延迟取决于 gather／scatter 的实作。在家用显卡上实际跑多快，才是我最在意的。
  • Qwen3.5 的大进步，有多少来自「回来」？ 作者的解释是混合架构里的线性注意力层需要完整的串行排列，而 Reroute 刚好没有把 token 移走。那么进步里有多少来自「保留串行排列」、有多少来自「让 token 回来」？如果有一组「保留排列但禁止回来」的对照，会清楚很多。
  • 有一个数字怪怪的。 VQA 表里，PDrop 留 192 个 token 时 TextVQA 是 46.9，留得更少的 128 个 token 却是 56.2。这一格如果有问题，192 个 token 那一组的平均差距就会被放大。
  • 救回来之后还是差很多。 就算加了 Reroute，Qwen2.5-VL 砍掉 88.9% 时也只剩原本的 18.6%。能找回一些，但离「完整找回」还有很长的距离。

读完之后想试的事

  1. 在短视频上照原样套 Reroute，看视频 token 的重要性是不是也会随深度漂移，像论文的 Figure 2 那样追踪一个关键 token。
  2. 做「保留串行排列但禁止回来」的对照组，把进步的来源拆开。
  3. 比较 token 回来时「保留原本的时间位置」和「重新编号」差多少。
  4. 在自己的显卡上量实际延迟，看 gather／scatter 的额外成本有多大。

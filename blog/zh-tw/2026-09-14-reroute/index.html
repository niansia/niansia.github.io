Reroute：丟掉的視覺 token，晚點還能撿回來嗎？

Reroute 把「刪掉低分的視覺 token」改成「先延後，之後還能回來」，不用訓練，壓得越狠救回越多。它處理的是圖片；我讀完一直在想，同樣的想法放到長影片上會碰到什麼。

2026-09-144 分鐘閱讀視覺語言模型視覺 token 壓縮定位長影片

arXiv 2026 · 精讀

Reroute, Don’t Remove: Recoverable Visual Token Routing for Vision-Language Models

Cheng-Yu Yang, Shao-Yuan Lo, Yu-Lun Liu

論文 ↗程式碼 ↗

為什麼讀這篇

現在大部分減少視覺 token 的方法都是同一個套路：打分數、留下高分的、把其他的刪掉，這篇卻直接質疑「刪掉」這個動作本身：被丟掉的東西，還有沒有機會回來？

這個問題在長影片上會更尖銳。畫面太多，一定要壓縮才放得進模型，可是後面的問題偏偏可能問到被壓掉的細節。Reroute 處理的是圖片，不是影片，但它從最小的地方切進了這個問題，所以我把它讀完。

這篇在做什麼

先看一個現象。 一個視覺 token 重不重要，會隨著解碼器的深度改變。論文追蹤了「穿綠色上衣的男人」這個描述裡，真正落在目標框內的一個 token：它的注意力百分位在第 3 層（FastV 做決定的地方）只有 0.11，在第 8 層（PDrop 做決定的地方）是 0.25，所以兩種方法都會把它刪掉；可是到第 25 層，它爬到了 0.97。淺層看起來跟背景沒兩樣的 token，到了深層卻是關鍵證據。

做法很簡單。 Reroute 沿用原本剪枝方法的打分方式（文字對影像的注意力）和同樣的分段排程，只改「打完分之後做什麼」：

  • 高分的 token 照常經過這一段的注意力和 FFN；
  • 低分的 token 不刪，只是這一段先跳過（走殘差路徑，表示維持不變），到下一個決策點再和全部視覺 token 一起重新排名，分數夠高就能回來。

原本的剪枝，就是「禁止回來」的特例。從公式看，兩者只差在下一段的候選集合：是上一段留下來的那些，還是全部。換個角度看，這就是不用訓練、拿注意力分數當路由器的 Mixture-of-Depths。因為每一段進入計算的 token 數一樣，理論上的 TFLOPs 和 KV cache 都跟原本的剪枝方法同一個等級。

結果

主要看定位任務（RefCOCO 系列，預測框的 IoU 大於 0.5 算對）。下面是 LLaVA-1.5-7B（HuggingFace 版本）的平均成績，以完整 576 個 token 的原模型當 100%：

平均留下的 token FastV FastV + Reroute PDrop PDrop + Reroute
192 45.5% 59.2% 71.3% 82.3%
128 19.8% 31.8% 53.4% 61.2%
64 0.6% 0.6% 22.2% 34.0%

幾個重點：

  • 壓得越狠，救得越多，但前提是要有「再看一次」的機會。 FastV 只在一層做一次決定，到 64 個 token 時幾乎救不回來；PDrop 分好幾段做決定，Reroute 就能從 22.2% 拉到 34.0%。
  • 換骨幹也成立。 Qwen2.5-VL-7B 砍掉 88.9% 的 token 時，PDrop 從 11.1% 到 18.6%；Qwen3.5-9B 這種混合架構進步最大，砍掉三分之二時 FastV 從 31.1% 直接到 77.5%。
  • 一般問答沒有變差。 在 GQA、TextVQA、MME 等八個 VQA 基準上，平均成績和原本的剪枝差不多或更好。
  • 計算量幾乎一樣。 留 64 個 token 時，PDrop + Reroute 的 TFLOPs 少 77%、KV cache 少 83%，跟 PDrop 本身差不多。
  • 另外值得一提：全部實驗都在一張 RTX 4090 上完成。

附錄裡我最在意的兩件事

第一，位置編號比想像中重要。 剪枝之後，留下的 token 可以重新編成連續的位置，也可以保留原本的位置編號。在 LLaVA-1.5 上用 FastV 留 192 個 token 時，重新編號會讓 RefCOCO testA 從 27.8 掉到 1.9，幾乎完全失去定位能力，token 本身還在，但模型已經不知道它「原本在哪裡」。

這個結果提醒我，位置資訊和 token 本身一樣重要。影片多了時間軸，這件事只會更重要。

第二，Qwen3-VL 上反而變差。 附錄的 Qwen3-VL-8B 實驗裡，砍掉三分之二的 token 時，PDrop 是 69.5%，加上 Reroute 反而掉到 57.2%；只有在砍掉 88.9% 這種極端情況，才從 12.9% 進步到 19.1%。作者的解釋是 Qwen3-VL 有 DeepStack（在前幾層額外注入視覺特徵），手動設定的排程得配合架構調整。這個結果只放在附錄，正文沒有提；但現在很多人用的正是 Qwen3-VL 系列，我覺得它反而是最重要的一張表。

放到長影片上：我在想的事

圖片只有幾百個 token，影片就不一樣了。讀完之後我一直在想，把「延後而不刪除」搬到長影片上，會碰到哪些問題：

  1. 候選池本身就是負擔。 Reroute 延後的 token 還留在序列裡，只是不參與計算。圖片的 576 個 token 當然留得住，長影片動輒幾萬個，全部的表示都留在顯卡上，本身就是記憶體問題。
  2. 重新排名的成本會跟著變大。 Reroute 每到一個決策點，都要拿所有候選 token 算一次注意力。候選從幾百個變成幾萬個時，光是「重新排名」這一步就不便宜了。
  3. 跳過太久的表示會不會過期？ 被延後的 token，表示停在它被跳過的那一層；如果好幾段之後才回來，它帶的還是淺層的特徵，卻要和深層的文字一起計算。論文沒有分析這件事，而在影片裡可能更嚴重：一個 token 可能同時在「深度」和「時間」上都落後。

我的疑問

  • 實際速度沒有量。 論文報的是理論上的 TFLOPs 和 KV cache，作者也承認實際延遲取決於 gather／scatter 的實作。在家用顯卡上實際跑多快，才是我最在意的。
  • Qwen3.5 的大進步，有多少來自「回來」？ 作者的解釋是混合架構裡的線性注意力層需要完整的序列排列，而 Reroute 剛好沒有把 token 移走。那麼進步裡有多少來自「保留序列排列」、有多少來自「讓 token 回來」？如果有一組「保留排列但禁止回來」的對照，會清楚很多。
  • 有一個數字怪怪的。 VQA 表裡，PDrop 留 192 個 token 時 TextVQA 是 46.9，留得更少的 128 個 token 卻是 56.2。這一格如果有問題，192 個 token 那一組的平均差距就會被放大。
  • 救回來之後還是差很多。 就算加了 Reroute，Qwen2.5-VL 砍掉 88.9% 時也只剩原本的 18.6%。能找回一些，但離「完整找回」還有很長的距離。

讀完之後想試的事

  1. 在短影片上照原樣套 Reroute，看影片 token 的重要性是不是也會隨深度漂移，像論文的 Figure 2 那樣追蹤一個關鍵 token。
  2. 做「保留序列排列但禁止回來」的對照組，把進步的來源拆開。
  3. 比較 token 回來時「保留原本的時間位置」和「重新編號」差多少。
  4. 在自己的顯卡上量實際延遲，看 gather／scatter 的額外成本有多大。
